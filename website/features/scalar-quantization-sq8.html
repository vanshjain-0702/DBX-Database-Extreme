Storage & density

SQ8 Scalar Quantization: Memory-Efficient Vector Search at Scale

8-bit scalar-quantized vectors in mmap'd files with asymmetric distance computation. ~4x memory savings over float32. Idle tenants live in page cache, not resident RAM.

01

Why Memory Density Matters for Multi-Tenant Vector Search

When you host 100 tenants on a single node, each with up to 100,000 vectors, float32 storage becomes prohibitively expensive. At 1536 dimensions (OpenAI's embedding size), float32 requires ~600 MB per tenant — that's 60 GB of RAM for the vectors alone across 100 tenants.

Most of those tenants are idle at any moment. Paying for resident RAM for every idle customer's vectors is waste. The metric that matters is cost per active tenant, not cost per provisioned tenant.

02

How SQ8 + mmap Achieves Density

DBX stores vectors as 8-bit scalar-quantized (SQ8) rows in memory-mapped files:

  • SQ8 quantization — each float32 component is mapped to a uint8 byte, reducing payload to ~¼ of float32
  • Asymmetric distance — the query vector stays in float32 while stored vectors are in uint8, preserving better accuracy than symmetric quantization
  • mmap storage — the OS pages in active tenants and pages out idle ones automatically
  • Page cache residency — idle tenants sit in the kernel's page cache, evicted under memory pressure without process management

How SQ8 Fits Into the Storage Architecture

A

Per-tenant data directory

Each tenant's SQ8 vector files, HNSW graph, WAL, and snapshots live in an isolated directory. Backup and delete operate on one customer's files.

B

Named spaces

Each named SPACE (text, image, code) creates separate mmap/HNSW files in the same tenant directory. All are SQ8. Quota and backup cover all spaces for that tenant.

C

Encryption boundary

In strict mode, the HNSW graph and WAL are encrypted under a per-tenant key. SQ8 .vec rows stay mmap plaintext so idle tenants remain cheap. Use fscrypt or LUKS for at-rest encryption of vector rows.
