# DBX v1.3.0 — memory you can evolve and operate

Released 2 October 2026.

DBX v1.3.0 brings the changes since v1.2.0 into one release: live vector
migration, historical vector search, LangChain and LlamaIndex integrations,
stronger Linux worker isolation, authenticated encrypted replication, and an
opt-in support extension with scoped diagnostics and audited tenant wake.

DBX remains a self-hosted, per-tenant memory engine for AI products. Its
supported single-node profile is 100 tenants per node, 100k vectors per tenant,
and durable strings plus vectors. Embeddings are supplied by the application.

## What changed since v1.2.0

### Evolve a tenant's vector memory

- `VMIGRATE START`, `ADD`, `SWAP`, and `CANCEL` build a shadow index while the
  current index remains searchable. Migration lifecycle operations are
  WAL-durable and covered by recovery regressions.
- `VSEARCH ... AS_OF <unix-nanoseconds>` reconstructs retained vector WAL
  history into a temporary index for retrieval audits and incident reproduction.
- Concurrent WAL writes preserve sequence order. Historical replay uses
  tenant-local scratch space and streams the requested key's history.

Migration requires caller-side re-embedding and temporary storage. Historical
search is slower than current search and is limited by WAL retention. Migration
lifecycle operations are not yet a replicated WAL protocol.

### Connect application frameworks

- The Python SDK includes LangChain and LlamaIndex vector-store adapters,
  optional dependency extras, and runnable RAG examples.
- Batch ingest is split into requests that respect the server's 1,000-vector
  limit. The RESP parser accepts larger arrays for large vector payloads.
- Dashboard navigation, tenant views, data inspection, and login were updated.
  The HTTP query endpoint accepts either a command string or an argument array.
- Legal Auditor and Jurix are included as example applications built around
  tenant-scoped memory and retrieval. Their application decisions remain
  separate from DBX's storage and isolation guarantees.

### Strengthen the deployment boundary

- Linux strict workers apply Landlock and `no_new_privs` across worker threads.
  Seccomp restricts socket creation to Unix sockets and blocks `io_uring` and
  foreign-ABI syscall paths. Strict worker binaries must use `CGO_ENABLED=0`.
- Worker `GOMEMLIMIT` is set to 90% of the tenant quota.
- WAL replication uses a mutual HMAC-SHA256 handshake, tenant-group keys, and
  per-connection AES-256-GCM encryption. Tampered and replayed frames are rejected.

Replication remains asynchronous: the primary acknowledges locally. Vector
payload `.vec` rows remain mmap plaintext; use encrypted storage when those
rows require at-rest confidentiality. See
[the isolation contract](https://github.com/vanshjain-0702/DBX-Database-Extreme/blob/v1.3.0/docs/isolation.md).

### Diagnose and recover within a defined scope

- The separately installed support extension reads an allowlisted tenant
  snapshot through a dedicated support capability.
- A distinct, optional wake capability can wake only allowlisted hibernated
  tenants. The server requires a durable pre-action audit and enforces a
  five-minute cooldown per tenant and orchestrator process. The client limits
  attempts and independently checks recovery.
- Structured WAL-recovery and tenant-task-panic codes support local log scans.
  Redacted bundles and bounded candidate learning stay on the operator's machine.
- The extension includes 31 casebook entries, 43 contract/fault tests, and
  1,340 repeatable synthetic drills with seed 17 and 20 variants. These are
  diagnostic and policy evaluations; they do not train model weights or prove
  automatic repair of arbitrary defects.

The support extension is versioned independently as `0.4.0`. It is disabled by
default and manually started. Code repair, restore, deletion, promotion, and
security/configuration changes are outside its executable recovery capability.
See [the support curriculum](https://github.com/vanshjain-0702/DBX-Database-Extreme/blob/v1.3.0/docs/support-recovery-curriculum.md).

## Upgrading from v1.2.0

1. Back up each tenant and retain the deployment's `DBX_KEK` and
   `replication.key`. Verify restore on a disposable node before replacing the
   running deployment.
2. Update the orchestrator image to
   `ghcr.io/vanshjain-0702/dbx-orchestrator:v1.3.0`, or build the tagged source
   with `deploy/Dockerfile`. Deploy the embedded dashboard and matching engine
   together. Standalone strict workers must be built with `CGO_ENABLED=0`.
3. Upgrade primary and replica peers together: v1.3.0's authenticated encrypted
   replication handshake requires matching peers. Preserve the replication
   key rather than generating unrelated keys on each peer.
4. Update the Python SDK from `sdk/python` if using the new framework adapters.
   Use the `langchain`, `llamaindex`, or `all` installation extras as needed.
5. Leave support capability variables empty to keep support disabled. To enable
   it, configure distinct read/wake tokens and exact tenant allowlists, then
   install and start the extension separately.

Keep the existing Linux strict/TLS/key configuration and verify tenant health,
scoped credentials, usage, backup/restore, and application retrieval after the
upgrade. The offline `dbx-v1-reset` tool is for incompatible pre-hardening
formats; it is not a routine v1.2.0-to-v1.3.0 upgrade step.

## Validation and performance context

Release checks cover the Go suite, vet and Staticcheck, Python lint/tests,
dashboard build/lint, support drills on Linux and Windows with Python 3.10 and
3.14, Linux race detection, and production coverage/isolation/vector gates.

The performance figures already on the site refer to the documented
27 August 2026 certification host and workload. This release announcement does
not claim a newly measured latency, throughput, or density improvement.
